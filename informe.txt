2. INTRODUCCIÓN Y REQUISITOS
--------------------------------------------------------------------------------

2.1. Problema o necesidad que resuelve la aplicación y usuarios objetivo:
En los salones de belleza y estudios especializados de manicure y pedicure, la gestión tradicional de citas se realiza comúnmente a través de cuadernos físicos o mensajes dispersos en aplicaciones de mensajería instantánea. Esta práctica manual acarrea problemas recurrentes:
a) Cruce involuntario de horarios y sobreventa de turnos entre distintas manicuristas.
b) Ausencia de confirmación o recordatorio formal para los clientes, lo cual genera inasistencias sin previo aviso.
c) Pérdida de tiempo del personal respondiendo cotizaciones de servicios y consultando disponibilidad de productos.
d) Falta de control sobre los abonos previos (señas) y registro contable de las ventas diarias del salón.

Nail's By es una plataforma web integral, rápida y accesible que digitaliza el agendamiento en tiempo real, calcula la disponibilidad exacta de horarios de cada profesional, ofrece un catálogo de productos con carrito de compras y brinda un panel administrativo con métricas financieras y seguimiento directo vía WhatsApp.

Usuarios objetivo:
1. Clientes: Personas que buscan consultar servicios de belleza de uñas, reservar turnos según fecha y manicurista preferida, comprar insumos de cuidado personal y revisar el estado de sus citas sin esperas.
2. Personal y Administración (Staff): Manicuristas y administradores del salón que requieren visualizar su agenda diaria, filtrar turnos por estado (pendiente, confirmada, completada, cancelada), registrar abonos monetarios, gestionar clientas y analizar las ventas del negocio.

2.2. Objetivo General:
Desarrollar una aplicación web accesible, responsive y modular para la reserva de citas y venta de insumos en el salón "Nail's By", empleando exclusivamente estándares W3C, HTML5 semántico, CSS3 adaptable y JavaScript nativo sin frameworks, garantizando plena operatividad por teclado y persistencia local de datos con arquitectura escalable hacia bases de datos relacionales.

Objetivos Específicos:
1. Diseñar una interfaz de usuario inclusiva, intuitiva y responsive basada en CSS Flexbox y Grid, cumpliendo con las pautas WCAG 2.2 Nivel AA en cuanto a contraste de color (mínimo 4.5:1), tamaños táctiles y ausencia de desbordamiento horizontal a 320 px.
2. Implementar un motor de lógica en JavaScript nativo con separación de responsabilidades para el cálculo de disponibilidad de horarios, control de turnos, gestión del carrito de compras y validación accesible de formularios en tiempo real mediante manipulación segura del DOM y eventos desacoplados (addEventListener).
3. Verificar y documentar el estricto cumplimiento de estándares web mediante las herramientas oficiales Nu HTML Checker, CSS Validation Service, WAVE y Lighthouse, asegurando un código limpio, operable solo con teclado y libre de errores.

* Explicación Técnica y Justificación:
En lugar de utilizar etiquetas genéricas `<div>`, se emplean elementos semánticos de HTML5 (`<header>`, `<nav>`, `<main>`, `<section>`, `<article>`) acompañados de atributos ARIA explícitos (`role="banner"`, `aria-label`, `aria-current="page"`). Esto permite que los motores de búsqueda y las tecnologías de asistencia (como lectores de pantalla NVDA o JAWS) puedan identificar inmediatamente la jerarquía estructural y saltar entre bloques de contenido sin ambigüedades.

* Explicación Técnica y Justificación:
Se emplea `display: grid` con la función matemática `repeat(auto-fill, minmax(250px, 1fr))` para que el catálogo distribuya automáticamente las columnas disponibles según el ancho del viewport. En pantallas móviles inferiores a 480 px, la media query conmuta la cuadrícula a `1fr` y ajusta los espacios interiores, eliminando todo riesgo de desplazamiento horizontal a 320 px (cumpliendo con la pauta WCAG 1.4.10 Reflow).

C) JavaScript: Eventos Desacoplados, Preselección de Fecha Hábil y Validación DOM:
Fragmentos representativos tomados de app.js (644 líneas):
```javascript
// Preselección inteligente del próximo día laborable abierto
function getNextOpenDateISO() {
  const d = new Date();
  if (d.getDay() === 0) {
    d.setDate(d.getDate() + 1); // Si hoy es domingo cerrado, pasar automáticamente al lunes
  } else if (d.getHours() >= 18) {
    d.setDate(d.getDate() + 1); // Si ya cerró el salón (18:00), pasar a mañana
    if (d.getDay() === 0) d.setDate(d.getDate() + 1);
  }
  const y = d.getFullYear(), m = String(d.getMonth() + 1).padStart(2, "0"), day = String(d.getDate()).padStart(2, "0");
  return `${y}-${m}-${day}`;
}

// Validación accesible con mensajes textuales y atributos ARIA
function setFieldError(input, errId, msg) {
  if (!input) return;
  input.setAttribute("aria-invalid", "true");
  input.setAttribute("aria-describedby", errId);
  const el = document.getElementById(errId);
  if (el) { el.textContent = msg; el.style.display = "block"; }
}

// Delegación central de eventos sin atributos en línea (onclick)
document.addEventListener("click", (e) => {
  const target = e.target.closest("[data-action]");
  if (!target) return;
  const act = target.getAttribute("data-action");
  if (act === "select-service") {
    state.booking.svcId = Number(target.getAttribute("data-id"));
    state.booking.time = "";
    renderBookingPage();
  }
});
```
* Explicación Técnica y Justificación:
Se erradicó cualquier presencia de manejadores en línea (`onclick="..."` o `onsubmit="..."`) en el marcado HTML, cumpliendo la regla de oro de la W3C. La función `getNextOpenDateISO` asegura que al abrir la pantalla de reservas siempre se presente un día hábil con sus horarios calculados de inmediato, evitando que el usuario quede bloqueado si visita el sitio en domingo o fuera del horario de atención.

5.3. Tres Ejemplos de Código Corregido (Antes y Después):

Ejemplo 1: Erradicación de eventos en línea (W3C HTML5 & WCAG 2.1.1 Operable por Teclado).
* Antes:
  ```html
  <button onclick="selectService(1)">Manicure clásico</button>
  ```
* Después:
  ```html
  <button type="button" role="radio" aria-checked="true" data-action="select-service" data-id="1">
    Manicure clásico
  </button>
  ```
* Justificación y Norma: La recomendación oficial W3C HTML5 prohíbe el acoplamiento de lógica mediante atributos inline como `onclick`, ya que vulnera la separación de capas y dificulta la auditoría de seguridad y accesibilidad. Al usar `data-action` y escuchar con `addEventListener`, el botón es operable nativamente por teclado con Enter y Espacio.

Ejemplo 2: Corrección de Contraste de Color en Texto (WCAG 2.2 Criterio 1.4.3 Nivel AA).
* Antes:
  ```css
  :root { --tx: #3a2530; --mu: #8a6f7b; --ac: #d6457a; }
  /* El color de acento #d6457a contra fondo blanco ofrecía un ratio de solo 3.8:1 */
  ```
* Después:
  ```css
  :root { --tx: #2b1722; --mu: #5e4753; --ac: #a82255; }
  /* El nuevo acento #a82255 contra fondo blanco ofrece un ratio certificado de 6.1:1 */
  ```
* Justificación y Norma: La pauta WCAG 1.4.3 exige una relación de contraste mínima de 4.5:1 para texto normal. El color rosa anterior (#d6457a) era ilegible para personas con debilidad visual o en pantallas expuestas a luz solar directa. Al recalibrar a #a82255, se superó el estándar llegando a 6.1:1.

Ejemplo 3: Indicación de Errores de Formulario Accesible (WCAG 1.4.1 Color y 3.3.1 Identificación).
* Antes:
  ```html
  <input id="email" style="border: 1px solid red;">
  ```
* Después:
  ```html
  <label for="auth-email">Correo electrónico <span aria-hidden="true">*</span></label>
  <input id="auth-email" type="email" aria-invalid="true" aria-describedby="err-auth-email" required>
  <span class="error-text" id="err-auth-email" role="alert">Ingresa un correo electrónico válido.</span>
  ```
* Justificación y Norma: WCAG 1.4.1 prohíbe transmitir información exclusivamente mediante el color, ya que usuarios con daltonismo no perciben bordes rojos. WCAG 3.3.1 exige que los errores se describan en texto. Al asociar el `<span>` con `aria-describedby` y `aria-invalid="true"`, el lector de pantalla lee de inmediato el motivo exacto del fallo.

5.4. Resultados de la Prueba de Navegación Solo con Teclado:
- Se recorrió la totalidad de la aplicación sin utilizar el ratón, empleando exclusivamente:
  * Tecla Tab: Avance secuencial en orden lógico y natural del DOM.
  * Teclas Shift + Tab: Retroceso secuencial sin bloqueos o trampas de foco.
  * Teclas Enter y Barra Espaciadora: Activación de botones, enlaces y tabs.
  * Tecla Escape: Cierre instantáneo de ventanas modales y retorno de foco al elemento invocador.
- El anillo de foco visual (`:focus-visible`) se mantiene permanentemente visible mediante un contorno de 3 px de grosor en color `--focus-ring` (#a82255) y un desplazamiento de 3 px, garantizando que el usuario siempre conozca la posición activa en la pantalla.

7. CONCLUSIONES, APORTES Y REFERENCIAS
--------------------------------------------------------------------------------

7.1. Conclusiones del Proyecto:
1. Se demostró la viabilidad técnica y pedagógica de construir una solución web moderna, robusta y escalable empleando exclusivamente tecnologías nativas (HTML5, CSS3 y JavaScript ES6+), prescindiendo de sobrecargas de rendimiento originadas por frameworks pesados o librerías de terceros.
2. La incorporación rigurosa de las pautas de accesibilidad WCAG 2.2 Nivel AA no representa una limitante para el diseño visual, sino que eleva la calidad integral del producto de software, asegurando que personas con capacidades diversas o que navegan únicamente con teclado disfruten de una experiencia fluida, digna y comprensible.
3. El desacoplamiento de la lógica del negocio en servicios independientes (StorageService, ValidationService, BookingService, CatalogService) sienta las bases sólidas para que la plataforma migre de manera inmediata hacia una arquitectura cliente-servidor con base de datos relacional (MySQL) sin tener que reescribir la capa de presentación.

7.2. Recomendaciones y Escalabilidad Futura (Siguientes Fases):
1. Migración de almacenamiento: Conectar las funciones de lectura y escritura de `StorageService` a una API REST construida en PHP o Node.js con base de datos relacional MySQL, implementando sentencias preparadas (PDO) y procedimientos almacenados para garantizar concurrencia multiusuario.
2. Seguridad y autenticación avanzada: Reemplazar el almacenamiento plano de contraseñas por un esquema de autenticación basado en JSON Web Tokens (JWT) y cifrado seguro de contraseñas mediante algoritmos como bcrypt o Argon2.
3. Pasarela de pagos en línea: Integrar una pasarela de pagos nacional/internacional (Payphone o Stripe) para el cobro automatizado del abono del 30% en el instante en que el cliente solicita el turno.
